# Limite de segurança do shell

O shell aprovado roda como o processo normal do Talos, sob o UID do app. No Android sem root, o sandbox por UID impede outros apps de ler `files/`, mas não impede esse shell: ele pode ler e alterar a memória, skills, conversas, configurações e outros arquivos privados acessíveis ao Talos. O gate pede consentimento para executar o comando; ele não torna esses dados invioláveis.

Uma mitigação real exigiria executar o shell sob outro UID. Um `Service` com `android:isolatedProcess="true"` recebe um UID isolado, sem as permissões do app e sem acesso ao diretório privado dele. Comandos nesse processo poderiam continuar a usar o shell e arquivos públicos acessíveis ao UID isolado, mas não poderiam operar no workspace privado atual nem chamar APIs protegidas do app por conta própria. Para recuperar essas funções, o Talos teria de oferecer operações estreitas por Binder; um broker genérico de arquivos ou comandos devolveria a capacidade de exfiltrar os dados e destruiria o limite. Isso exigiria redesenhar o contrato das ferramentas e quebraria usos reais que dependem de arquivos privados e APIs do app. Portanto, não é uma troca proporcional para o harness atual, embora seja a direção para uma futura arquitetura de capacidades menores.

Usar outro diretório de trabalho, limpar variáveis de ambiente ou remover variáveis do processo não muda o UID nem o acesso concedido pelo sandbox. Um filtro textual de comandos também não cobre shell, pipes, expansão, scripts, links simbólicos ou ferramentas auxiliares; não constitui um limite de segurança. A recomendação imediata é ser explícito no gate: aprovar shell autoriza acesso aos arquivos privados do app. A UI agora mostra esse aviso para cada aprovação de shell. Isso melhora o consentimento informado, mas **não** reduz as capacidades do comando; os dados continuam acessíveis ao shell aprovado.
